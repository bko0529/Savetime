## 알게 된 점
1. **Artillery 작업자는 `config.payload`를 각자 첫 줄부터 읽어요.** `order: sequence`라도 작업자 7개가 같은 줄을 써서, 대원 300명이 실제로는 약 60명(같은 대원 5번)이었어요. 처음 결과는 이 때문에 틀렸어요. `processor.mjs`의 `pickPc`·`pickMedic`·`pickMoving`이 줄마다 '찜' 폴더를 만들어 한 줄은 한 명만 쓰게 고쳤어요(폴더 만들기는 동시에 해도 한 곳만 성공). S1의 병원 PC 연결 연습도 같은 이유로 PC가 겹쳤을 수 있어요
2. **`ensure`는 `config.plugins.ensure`를 켜야 판정해요.** S1에 알았는데 새 시나리오(`locations.yml`)에서 또 빠뜨렸어요. 이송 만들기 p95가 12초인데 exit 0이어서 알았어요
3. **위치 기록은 경로 안내 담당 단말만 할 수 있어요**(SFR-132, `NOT_NAV_DEVICE`). 부하용 이송 건에 담당 단말을 미리 정해 둬야 해요
4. **요청이 가는 병원은 '알림 켠 근무가 있는 PC'가 있는 병원뿐이에요.** 부하용 병원에 근무를 만들고, 병원 봇이 붙을 때 `alarm.resume`으로 알림을 켜요
5. **요청 → 병원 알림 시간은 서버가 준 값으로 잴 수 있어요.** 회차의 응답 마감은 DB가 '보낸 시각 + 2분'으로 정해서, 받은 시각 − (마감 − 2분)이 이송 만들기 → 커밋 → 전송까지의 시간이에요
6. **내 컴퓨터의 Docker Desktop이 부하 중에 한 번 멈췄어요.** 위치 기록 첫 실행이 75초쯤 DB 연결 끊김으로 실패해서 다시 쟀어요

## 이송 만들기가 느린 이유 (추정, 백강욱 님 확인 부탁)
- 이벤트를 쓰는 트랜잭션은 모두 `appendEvents`(`server/src/modules/realtime/eventLog.ts`)에서 **전역 잠금 하나**(`pg_advisory_xact_lock`)를 잡고 **커밋(디스크 기록 확인)까지** 쥐어요. 이송 만들기·승인·확정이 서버 전체에서 한 줄로 서요
- 느린 실행에서는 병원 승인이 많이 성공했어요(약 2,600~2,850건). 빠른 실행(3번)은 대원이 금방 확정해서 나머지 요청이 닫혀 승인 성공이 383건이었어요
- 승인이 한 줄 서기가 감당할 양을 넘으면 → 이송 만들기·확정이 줄 뒤에서 기다리고 → 그사이 요청이 오래 열려 승인이 더 몰리고 → 더 느려지는 눈덩이 모양이에요
- 3번 실행 동안 DB 연결 대기 이유를 1초마다 봤을 때 `Lock/advisory`(위 잠금)와 `IO/WALSync`·`LWLock/WALWrite`(커밋 디스크 기록)가 보였어요
- 서버 DB 연결은 pg 기본값 10개예요(`new pg.Pool`에 `max` 없음)
- 병원 봇은 **모든 요청을 승인**하는 최악의 경우예요. 실제로는 병원마다 거절도 섞여요
- 알림 목표(3초)는 모두 통과했지만, 대원이 '요청 보내기'를 누르고 10초 넘게 기다리면 현장에서는 실패로 느껴져요

## S8에서 할 일
- 클라우드 부하 서버에서 `perf/run-s8.sh`로 PER-005(병원 PC 1,230 + 대원 앱 3,300 동시 유지) 중에 PER-006·007을 함께 재고, PER-008을 따로 재기
- 이송 만들기 지연이 클라우드(디스크가 빠른 서버)에서도 나오는지 확인 → 나오면 잠금 범위·DB 연결 수 조정 (백강욱)
- 시험 환경: 준비 스크립트는 `NODE_ENV=production`에서 거부돼요. 운영 DB에 부하용 병원이 생기면 실제 요청이 그 병원으로 갈 수 있어서, **시험용 DB**를 쓰는 서버에 부하를 줘야 해요 (어떻게 띄울지는 백강욱 님과 정하기)
