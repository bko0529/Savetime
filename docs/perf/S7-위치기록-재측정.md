# S7 위치 기록 재측정 (PER-008)

- 날짜: 2026-11-11
- 담당: 백강욱 (결과 분석·튜닝, D-109). 시나리오는 윤승언 작성(`perf/locations.yml`, #83·#85)
- 목적: 승언 님 연습(#83)에서 빠진 일을 넣고 다시 잰다
  1. **확정 병원 요청이 있는 이송 건**: 실제 이동 중처럼 위치 저장 때 남은 시간 저장·입구 200m 판정(`afterLocations`)까지 돈다
  2. **내비 남은 시간**: 1분에 한 번 `etaMin`을 같이 보낸다 (SFR-121)
  3. **위치 이상치 판정**(SFR-040, #87): 저장마다 직전 정상 좌표와 비교하는 쿼리
- **목표값 확인용 실측은 아니에요.** 실측은 S8 클라우드에서 해요 (기술정의서 '부하 발생 위치')

## 환경
| 항목 | 값 |
|---|---|
| PC | MacBook Pro (Apple M5 Pro, 15코어, 메모리 24GB). 부하 도구와 서버가 같은 PC |
| 서버 | `main` 1대, `NODE_ENV=production`, 로그 warn, Node.js 24 |
| DB·Redis | `docker compose` (PostgreSQL 16, Redis 7), 부하 전용 빈 DB |
| 코드 | main + #85 + #87(이상치) |
| Artillery | 2.0.34 (`npx`) |

|---|---|---|---|---|---|---|
| 목표 부하 | 300건 × 5초, 2분 | 60 | 7,200 | 204 × 7,200 | 8.9ms / **10.9ms** / 13.1ms / 37ms | 0 |

- 목표(95%를 1초 안)보다 약 **90배 여유**가 있어요. 3배 부하에서도 응답 시간이 거의 늘지 않았어요
- 서버 오류 로그(level 50) 0건

## 실제로 다 돌았는지 확인 (목표 부하, DB 조회)
| 항목 | 값 | 뜻 |
|---|---|---|
| 저장된 위치 점 | 7,200 | 요청마다 1점, 빠진 것 없음 |
| 이상치로 표시된 점 | 0 | 시나리오 이동 속도(5초에 약 35m)는 기준(초속 60m)보다 느림 → 정상 |
| 남은 시간이 저장된 이송 | 300 / 300 | `afterLocations`가 확정 요청을 찾아 돌았음 |
| `transport.eta`·`incoming.updated` 이벤트 | 각 300 | 처음 받은 값만 알림. 1분 뒤 값은 보여 줄 분이 같아 보내지 않음(설계대로) |

## 판단
- **튜닝할 것 없음.** 위치 저장 한 번에 쿼리가 여러 번 돌지만(잠금, 저장, 이상치 판정 2번, 확정 요청 조회, 입구 거리) 모두 이송 건 하나의 행·인덱스만 봐서 가벼워요
- 이송 건마다 잠금(`FOR UPDATE`)을 잡지만 담당 단말 1대만 보내서 서로 기다리는 일이 없어요

## S8 클라우드 실측 때 볼 것
- 서버와 부하 도구를 다른 서버로 나눠서 같은 두 실행을 다시 하고, 데이터 서버(DB) CPU를 같이 본다. 앱 서버와 DB가 다른 서버라 네트워크 왕복만큼 늘어날 것
- 준비: `npm run perf:medics -w server -- 300 300` (토큰 15분 안에 실행). 3배는 `-- 900 900` + `--overrides '{"config":{"phases":[{"duration":5,"arrivalRate":180}]}}'`
